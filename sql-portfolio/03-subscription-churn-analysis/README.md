# Subscription Churn Analysis — SQL Mini Project

An advanced SQL project simulating a subscription business (think SaaS or
streaming service). Unlike the other two projects, the raw data here is
**deliberately messy** — this is meant to mirror real-world data work, where
cleaning comes before analysis.

##  What's different about this one

- Starts from a messy `raw_subscribers` table: inconsistent email casing,
  stray whitespace, two different date text formats, and duplicate signups
- Includes a full **data cleaning pipeline** (dedupe, normalize, parse dates)
- Builds a **cohort retention matrix** — a real analytics deliverable, not
  just a single query
- Demonstrates **indexing and `EXPLAIN ANALYZE`** for query performance

##  Files

| File | Purpose |
|---|---|
| `subscription_churn_analysis.sql` | One self-contained file, in order: schema (including the messy `raw_subscribers` staging table), seed data, data cleaning, cohort retention analysis, and indexing/performance — each section's real output included as a comment block |

##  Setup

```bash
createdb churn_analysis
psql -d churn_analysis -f subscription_churn_analysis.sql
```

The output comments in the file were generated by actually running this exact
schema and data (data cleaning, cohort math, and churn metrics were all
verified against real execution). One exception: Section 5's `EXPLAIN
ANALYZE` output shows the query-plan *shape* — the concept it's teaching —
since exact cost/timing numbers depend on your PostgreSQL instance; run it
yourself with `psql` to see your own numbers.

##  What this project demonstrates

- **Data cleaning in SQL**: `TRIM`, `LOWER`, `DISTINCT ON`, conditional date
  parsing with `TO_DATE` across mixed formats
- **Cohort analysis**: `GENERATE_SERIES` to explode date ranges, `DATE_TRUNC`
  to bucket by month, month-difference math for "months since signup"
- **Business metrics**: churn rate, average subscriber lifetime, MRR lost
  to churn
- **Query performance**: reading `EXPLAIN ANALYZE` output, choosing single
  vs. composite indexes, and knowing why an index isn't always used on
  small tables

##  Possible extensions

- Add a `plan_changes` table to track upgrades/downgrades and their effect
  on churn
- Build a proper cohort *matrix* view (months as columns) using
  `CROSSTAB` or conditional aggregation
- Load a larger synthetic dataset (10k+ rows) to actually see the
  index performance difference in `EXPLAIN ANALYZE` output
